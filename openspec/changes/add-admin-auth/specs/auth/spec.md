## ADDED Requirements

### Requirement: User accounts are stored in the database
The system SHALL store user accounts in a `users` table holding a unique email, a password
hash, an active flag and an admin flag (`is_superuser`). Emails SHALL be normalised to
lowercase with surrounding whitespace removed before they are stored or compared. The table
SHALL serve all users, admin and non-admin alike.

#### Scenario: Email is unique regardless of case
- **WHEN** a user exists with email `admin@example.com` and an account is created for `Admin@Example.com`
- **THEN** the creation is rejected and no second row is stored

#### Scenario: New accounts are non-admin by default
- **WHEN** an account is created without requesting admin
- **THEN** it is stored active with `is_superuser` false

### Requirement: Passwords are stored only as argon2 hashes
The system SHALL hash passwords with argon2 through the `pwdlib` library and SHALL NOT store,
log or return a plaintext password. When a successful login finds a stored hash that uses
outdated parameters, the system SHALL replace it with a freshly computed hash.

#### Scenario: Stored value is a hash
- **WHEN** an account is created with a password
- **THEN** the stored `hashed_password` is an argon2 hash and does not contain the password

#### Scenario: Outdated hash is upgraded on login
- **WHEN** a user whose stored hash uses outdated parameters logs in with the correct password
- **THEN** the login succeeds and the stored hash is replaced with one using current parameters

### Requirement: Password login creates a session
The system SHALL expose `POST /api/v1/auth/login`, accepting an email (in the form's
`username` field) and a password as form data. On valid credentials for an active user it
SHALL create a session, respond `204`, and set the session cookie. Password verification
SHALL NOT block the event loop.

#### Scenario: Successful login
- **WHEN** an active user posts their correct email and password
- **THEN** the response is `204`, a session row exists for that user, and the response sets the `localdash_session` cookie

#### Scenario: Email is matched case-insensitively
- **WHEN** a user stored as `admin@example.com` logs in as ` Admin@Example.com ` with the correct password
- **THEN** the login succeeds

### Requirement: Failed logins are indistinguishable
The system SHALL respond to an unknown email, a wrong password and an inactive account with
the same `401` status and the same body, SHALL set no cookie, and SHALL create no session.
The unknown-email path SHALL still perform a password hash verification so that response
time does not reveal whether an email is registered.

#### Scenario: Wrong password
- **WHEN** a login is posted with a registered email and a wrong password
- **THEN** the response is `401`, no cookie is set and no session is created

#### Scenario: Unknown email matches wrong password
- **WHEN** a login is posted with an email that has no account
- **THEN** the response status and body are identical to the wrong-password response, and a hash verification was performed

#### Scenario: Inactive account
- **WHEN** a user with `is_active` false posts their correct password
- **THEN** the response status and body are identical to the wrong-password response and no session is created

### Requirement: Sessions are server-side, hashed and expiring
The system SHALL represent a session as a random token of at least 256 bits generated by a
cryptographically secure source. The database SHALL store only a SHA-256 hash of the token,
with the user and an expiry `auth_session_days` (default 7) after creation. A session SHALL be
valid only while its row exists, its expiry is in the future and its user is active.

#### Scenario: Token is not stored in plaintext
- **WHEN** a session is created
- **THEN** no column of the `sessions` row contains the token sent to the browser

#### Scenario: Expired session is rejected
- **WHEN** a request presents a session cookie whose expiry has passed
- **THEN** the request is treated as unauthenticated

#### Scenario: Deactivated user loses access
- **WHEN** a user with a valid session is set inactive and then makes a request
- **THEN** the request is treated as unauthenticated

#### Scenario: Unknown token is rejected
- **WHEN** a request presents a session cookie value that matches no session
- **THEN** the request is treated as unauthenticated

### Requirement: Session cookie attributes
The session cookie SHALL be named `localdash_session` and SHALL be set with `HttpOnly`,
`SameSite=Lax`, `Path=/` and a `Max-Age` equal to the session lifetime. It SHALL carry the
`Secure` attribute when the `auth_cookie_secure` setting is true, which is the default.

#### Scenario: Default attributes
- **WHEN** a login succeeds with default settings
- **THEN** the `Set-Cookie` header has `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` and a `Max-Age` of 7 days

#### Scenario: Secure disabled by setting
- **WHEN** a login succeeds with `auth_cookie_secure` false
- **THEN** the `Set-Cookie` header has no `Secure` attribute and keeps the other attributes

### Requirement: Current user endpoint
The system SHALL expose `GET /api/v1/auth/me`, returning the authenticated user's id, email
and admin flag, and SHALL respond `401` when the request is unauthenticated. The response
SHALL NOT include the password hash.

#### Scenario: Authenticated
- **WHEN** a request with a valid session cookie calls `/api/v1/auth/me`
- **THEN** the response is `200` with that user's `id`, `email` and `is_superuser`, and no password field

#### Scenario: Unauthenticated
- **WHEN** a request without a session cookie calls `/api/v1/auth/me`
- **THEN** the response is `401`

### Requirement: Logout revokes the session
The system SHALL expose `POST /api/v1/auth/logout`, which deletes the session named by the
request's cookie, clears the cookie and responds `204`. It SHALL respond `204` even when the
request has no valid session.

#### Scenario: Logout ends the session
- **WHEN** an authenticated request calls logout and the same cookie is then used on `/api/v1/auth/me`
- **THEN** logout responds `204` and clears the cookie, the session row is gone, and `/api/v1/auth/me` responds `401`

#### Scenario: Logout without a session
- **WHEN** a request without a session cookie calls logout
- **THEN** the response is `204`

#### Scenario: Other sessions are unaffected
- **WHEN** a user with two sessions logs out of one
- **THEN** the other session remains valid

### Requirement: Access-check dependencies
The system SHALL provide a `current_user` dependency that yields the authenticated active
user and responds `401` otherwise, and a `require_admin` dependency that additionally
responds `403` when the authenticated user is not an admin.

#### Scenario: Unauthenticated request to a protected route
- **WHEN** a request without a valid session reaches a route guarded by `current_user` or `require_admin`
- **THEN** the response is `401`

#### Scenario: Non-admin on an admin route
- **WHEN** an authenticated user with `is_superuser` false reaches a route guarded by `require_admin`
- **THEN** the response is `403`

#### Scenario: Admin on an admin route
- **WHEN** an authenticated user with `is_superuser` true reaches a route guarded by `require_admin`
- **THEN** the route handler runs and receives that user

### Requirement: Accounts are managed by an operator command
The system SHALL provide a command-line interface, `python -m app.auth`, with a `create-user`
command (email, optional admin flag) and a `set-password` command (email). The password SHALL
be read from an interactive prompt or standard input, never from a command-line argument, and
SHALL be rejected when shorter than 12 characters. `set-password` SHALL delete all of that
user's sessions. The HTTP API SHALL NOT offer account registration.

#### Scenario: Create an admin
- **WHEN** an operator runs `create-user --email admin@example.com --admin` and supplies a valid password
- **THEN** an active user with `is_superuser` true exists and can log in with that password

#### Scenario: Short password is rejected
- **WHEN** an operator supplies a password shorter than 12 characters
- **THEN** the command exits with an error and no account is created or changed

#### Scenario: Duplicate email is rejected
- **WHEN** an operator runs `create-user` for an email that already has an account
- **THEN** the command exits with an error and the existing account is unchanged

#### Scenario: Setting a password revokes sessions
- **WHEN** an operator runs `set-password` for a user who has active sessions
- **THEN** the new password works, the old one does not, and all of that user's sessions are deleted

#### Scenario: No registration endpoint
- **WHEN** the application's routes are listed
- **THEN** the only routes under `/api/v1/auth` are `login`, `logout` and `me`

### Requirement: Expired sessions are cleaned up
The system SHALL run a scheduled job that deletes sessions whose expiry has passed and
leaves unexpired sessions untouched.

#### Scenario: Cleanup removes only expired sessions
- **WHEN** the cleanup runs with one expired and one unexpired session stored
- **THEN** the expired session is deleted and the unexpired session remains
